# AGENTS.md

MCP server for a service desk, part of [MCP Platform](https://github.com/aiwcorpo/mcp-platform). Only the platform gateway
calls it (internal JWT, policy data pushed to `/.well-known/mcp-policy-data`). It is built on `mcp-platform-starter` (repo
`mcp-starter-lib`) and follows the contracts of `mcp-contracts` (versions in `pom.xml`). It calls the service desk with the
platform's service account (`accepted-credential-types: [service-account]` in `application.yml`), so the queue scope of the
user is enforced by this server and the policies. README and [CONTRIBUTING.md](CONTRIBUTING.md) hold the details.

## Commands

Maven needs JDK 25. With JDK 21 the build fails with `release version 25 not supported`. On macOS with Homebrew:

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home
./mvnw -B verify                    # what GitHub, GitLab and Jenkins run; about 30 s, no Docker, no service desk
./mvnw -B test -pl mcp-app -am -Dtest=ManifestTest -Dsurefire.failIfNoSpecifiedTests=false   # one test class
docker build -t mcp-servicedesk:dev .
```

There is no separate lint or format step. ERROR lines in the test output come from negative tests; the exit code decides.

## Layout

- `mcp-core` -> `mcp-application` (use cases, queue check) -> `mcp-integration` (REST adapter, resolvers) -> `mcp-tools` ->
  `mcp-app` (jar, end-to-end tests). Unit tests sit in each module; end-to-end tests with `TestGateway` and `StubBackend` (the
  reference layout) in `mcp-app/src/test`.
- `mcp-integration/.../ServicedeskApi.java` and `ServicedeskApiProperties.java`: the configurable REST shape. The reference
  layout is the `servicedesk.api` block of `mcp-app/src/main/resources/application.yml`.
- `mcp-app/src/main/resources/mcp/policies/`: Cedar schema and policies, shipped in the manifest.
- `mcp-app/target/mcp-manifest.json` is generated by the build; never commit it or edit it by hand.

## Hard rule: no product-specific code

No service desk product is chosen. The adapter is a generic REST client driven by `servicedesk.api`: paths, parameters, method
and JSON pointers. Do not add code paths, classes, profiles or `if` branches for a named product (Jira Service Management,
ServiceNow, Zendesk, OTRS and so on). If a product cannot be expressed, extend the configuration in a product-neutral way,
validate the new key at startup like the existing ones, document it in the README table and test it against `StubBackend`.

## Other rules

- Tool arguments never become part of a path: ids and search text go in only as strictly encoded URI variables, the note text
  as a JSON value. Config paths allow only letters, digits, `/_.-` and the placeholders.
- Keep the note marker: every note starts with `[Added through the MCP platform on behalf of <user>]`, the user comes from the
  gateway token, and text containing the marker phrase is rejected.
- A ticket the caller may not see, a missing ticket and a failed read all answer `not_found_or_denied`. Do not make them
  distinguishable. `add_note` re-reads the ticket and checks grants right before writing.
- Subject and description reach the model as `UntrustedText`, never as instructions.
- Tool definitions and the policies are part of the manifest that an administrator approves: a changed tool changes its
  `definitionHash`, a changed policy file changes `policiesHash`, and both need a new approval. Say so in the PR.
- A new tool follows the tool guide linked in CONTRIBUTING.md: risk, title, `@ResourceRef` for every id, closed argument schema,
  a negative test, a row in the README tools table.
- Interface changes (resource type, query field, credential type) start as a `proposed` entry in `CONTRACT_CHANGES.md` of
  `mcp-contracts` and need a person's approval before code here changes.
- Never log credentials or service desk response bodies; follow the existing `event=... key=value` log style.
- Test methods are camelCase sentences (`addsAnInternalNoteAfterReadingTheTicket`). Tests use `StubBackend` and dummy data only.
- The `dev` profile is for loopback runs; never put it in an env file, a systemd unit, `deploy/` or the image.
- CHANGELOG.md: newest first. 2.0.0 is released (tag `v2.0.0`); put new entries under `## Unreleased` at the top.
- Workflow actions are pinned to full commit SHAs and images (CI, `Dockerfile`) to digests. Keep it that way when bumping.

## Boundaries

Ask a person before: pushing to main, tagging, changing the version in `pom.xml`, running `release.yml`, publishing an image
(images go to `ghcr.io/aiwcorpo` only), or connecting to a real service desk or account. Never commit `.env` files, `mcp-*.env`
files other than the tracked `deploy/` ones, certificates, keys, tokens, `local-gateway.env`, internal host names or IP
addresses.

## Pull requests

One change per PR. Commit subject in English, imperative, up to 72 characters; the body says why, not how it was done. Tests go
in the same commit as the code. `./mvnw -B verify` must pass. Update README and CHANGELOG when a tool, setting or visible
behaviour changes. See [CONTRIBUTING.md](CONTRIBUTING.md).
